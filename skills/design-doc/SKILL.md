# design-doc

本 Skill 用于开发需求的设计阶段。

目标是把需求背景和实现逻辑讲清楚，形成一份：

- 人能够顺畅阅读、判断方案是否正确的设计文档；
- Codex 能够据此实现，而不需要在开发阶段重新猜测重要设计；
- 信息完整但不过度冗长，尽量降低阅读和上下文成本。

设计文档不是讨论过程的记录，也不是代码实现说明书。它应保留实现所需的关键设计结论，并让这些结论容易被人工 Review。

完整写作原则见 `principles.md`。遇到缓存、批量、异步、模型、迁移等具体机制时，使用 `obligations.md` 检查容易遗漏的设计细节。

## 1. 先理解需求和现状

写文档前先读取与需求直接相关的代码、已有文档和上下文，确认：

```text
为什么要做这个需求？
当前系统是怎样的？
现在的问题或限制是什么？
这次具体要改变什么？
哪些东西明确不在本次范围内？
```

背景只保留理解方案所必需的信息。

不要大段复述需求讨论、历史聊天或可以直接从代码看出的普通事实。背景的作用是让第一次 Review 这份文档的人知道“为什么需要这个设计，以及它在现有系统的什么位置”。

如果关键信息无法从需求或仓库确认，显式列为待确认项，不要自行补造事实。

## 2. 先定义关键概念和语义

复杂需求通常先把概念讲清楚，再讲实现。

优先明确会影响后续理解的内容，例如：

```text
核心对象是什么
几个容易混淆的对象有什么区别
ID / 时间 / 状态 /范围分别使用什么语义
数据由谁拥有
哪些结果是证据，哪些结果会真正产生修改
```

定义应短而精确，只解释“它是什么以及在本文中的语义”，不写长篇背景故事。

示例：

```text
Material
用户导入的原始媒体对象，时间使用素材源时间。

Segment
草稿中对 Material 的一次引用和变换结果，时间使用片段内相对播放时间。
```

如果多个后续模块共享同一规则，应尽早说明；局部章节仍可压缩重复与自身强相关的关键语义，避免读者频繁跳转。

## 3. 设计实现逻辑

先把系统如何工作推演清楚，再组织 Markdown。

根据当前需求识别真正需要设计的对象，例如：

```text
Capability
Component
Interface / API / CLI
Data Model
Workflow / State
External Dependency
Cache
Batch
Async / Retry / Concurrency
Persistence / Migration
Model / Agent
```

没有相关机制就不要为了形式完整增加章节。

对主要设计对象至少想清楚：

```text
它负责什么？
输入是什么？
输出是什么？
依赖谁？
关键数据如何流动？
哪些规则必须始终成立？
失败和边界情况如何处理？
```

出现具体机制时，再按 `obligations.md` 补齐容易遗漏的细节。

## 4. 用自然伪代码表达流程

两步以上的数据转换、调用顺序、状态变化和责任边界，优先使用接近自然代码的伪代码，而不是长段散文。

推荐记法：

```text
变量名<返回类型或返回内容> = 能力(输入)
```

例如：

```text
effective_range<{start_s, end_s}>
  = target.time_range ?? get_full_range(target.id)

frames[{time_s, image}]
  = get_frames(target.id, effective_range, fps ?? auto)

matched_ranges[{start_s, end_s, description}]
  = VLM[model, pe](query, frames)

ranges[{start_s, end_s, description}]
  = validate_and_merge_ranges(matched_ranges, limit=effective_range)
```

要求：

- 左侧写真实语义，不使用模糊的 `result`、`data`、`processed_result`；
- 表达关键数据流和控制流，不展开语言级样板代码；
- 影响行为的条件分支必须显式写出；
- 伪代码应比对应散文更容易让人 Review，而不是为了形式化而形式化。

## 5. 为不同信息选择合适的表达方式

Markdown 结构服务于理解，不要求固定模板。

| 信息 | 优先表达 |
| --- | --- |
| 关键术语和语义 | 简短 Definition |
| API、CLI、能力边界 | Contract / 函数式签名 |
| 多步实现逻辑 | Typed Pseudocode |
| 条件与行为矩阵 | Table |
| 模块、调用、状态关系 | Diagram |
| 必须始终成立的约束 | Rule / Invariant |
| 容易误解的具体用法 | Example |
| 重要取舍 | 简短 Decision / Reason |
| 尚未确定但影响实现的问题 | Open Question |

自由散文用于串联上下文和解释不适合结构化表达的内容，不要让整篇文档退化成长篇文章。

图只有在能明显降低关系理解成本时才使用；字段、错误码、边界等精确规则不要只放在图里。

示例用于帮助理解，不能成为某个行为唯一的规范来源。

## 6. 组织成适合人工 Review 的文档

最终目录根据方案自然形成，不要求每份文档拥有相同章节。

通常按“先建立共同理解，再逐步进入实现细节”的顺序组织：

```text
背景与目标
  ↓
关键概念 / 全局语义
  ↓
整体方案
  ↓
核心模块或能力的具体设计
  ↓
必要的横切机制
  ↓
实现边界与待确认项
```

实际文档只保留有价值的部分。

一个 Capability 可能自然写成：

```text
能力说明
输入输出
实现伪代码
关键规则
必要示例
```

一个 Data Model 可能更适合：

```text
定义
Schema
Invariant
Ownership
Lifecycle
```

一个异步 Runtime 可能更适合：

```text
状态
执行流程
中断与恢复
失败和幂等规则
```

不要为了统一格式强迫不同类型的设计使用同一套小标题。

## 7. 保证局部可理解

优先保证信息局部性。

读者 Review 一个具体能力或模块时，应在附近得到理解它核心行为所需的信息，而不是连续跳到多个章节拼接语义。

不要只写：

```text
失败处理见公共错误协议。
```

更适合写：

```text
单 target 失败不影响其他 target；批量结果保留失败 item 的 error。
完整错误码见公共错误协议。
```

先给当前设计单元需要的压缩结论，再在确实需要完整枚举或背景材料时引用其他位置。

可以适度重复已经压缩后的关键规则，但不要重复完整解释和推理过程。

## 8. 把实现阶段会影响正确性的细节写完

设计不需要规定普通代码细节，但不能把会影响行为正确性的决定留给实现阶段临时选择。

重点检查：

```text
数据和时间语义
输入输出协议
模块职责和 owner
正常流程
失败和空结果
边界值和非法输入
状态变化
批量 partial failure
重试与幂等
缓存一致性和失效
并发与资源上限
兼容和迁移
外部依赖失败
模型证据不足或输出非法
安全与数据可见边界
```

只检查当前方案实际涉及的项。

如果两种实现都会“看起来合理”，但会产生不同的产品行为、数据语义、协议、一致性或兼容结果，就应该在文档中明确选择。

仍未确定的重要问题必须显式写成待确认项。

## 9. 压缩文档

设计逻辑闭合后，再做一次压缩。

删除：

```text
讨论历史
重复解释
无信息连接句
已经由表格或伪代码完整表达的散文复述
与当前设计无关的背景
实现者可直接从代码稳定获得的普通细节
```

保留：

```text
必要背景
概念定义
设计逻辑
数据流和接口
关键规则
失败与边界
重要约束
实现边界
待确认项
必要的设计理由
```

目标不是最短，而是让每一段都对理解、Review 或实现有价值。

## 10. 完成前自检

最终以一个第一次看到该需求的 Reviewer 和一个随后负责实现的 Codex 的视角重新阅读文档。

Reviewer 应能够回答：

```text
为什么做？
方案解决了什么？
核心设计是否合理？
关键行为和边界是否符合预期？
有哪些重要取舍或待确认项？
```

Codex 应能够回答：

```text
需要改哪些系统边界？
主要数据和控制流是什么？
各模块分别负责什么？
输入输出和错误行为是什么？
关键边界和约束是什么？
```

重点寻找：

```text
只有作者自己知道的隐含前提
只有示例却没有规则的行为
只写 happy path 的流程
出现缓存、批量、异步等机制却没有说明关键语义
前后术语或协议不一致
实现时仍必须临时决定、且会影响外部行为的重要问题
```

发现后直接完善设计或明确标记待确认，不要通过增加无价值章节来掩盖问题。
