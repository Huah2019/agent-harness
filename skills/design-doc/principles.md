# Design Writing Principles

本文件定义 design-doc 的表达原则。目标不是统一文章格式，而是让设计语义以低歧义、低跳转、低 token 成本的方式表达。

## 1. 语义完备优先，形式完备不重要

设计文档必须覆盖实现所需的重要语义，但不要求固定章节、固定长度或固定模板。

评价设计是否完成时，优先判断：

- 实现 Agent 是否仍需自行决定外部行为或架构职责；
- 是否存在隐藏前提；
- 是否只描述了 happy path；
- 是否存在多种合理解释而文档未选择；
- 是否需要依赖此前聊天才能理解。

## 2. 最小充分表示

Design Doc 不是推理过程的记录，而是设计完成后的压缩表示。

保留最终成立的定义、规则、数据流、边界、失败语义、状态和关键取舍；删除为了证明“为什么一路想到这里”而产生的讨论历史。

复杂设计可以长，但每一段都应改变读者对系统的理解或实现方式。

## 3. 信息局部性优先于机械 DRY

局部设计应尽量自洽。

重复一个压缩后的关键规则，通常比强制读者跨章节跳转更好。引用适合完整枚举、低频细节和补充背景，不应承担局部行为的核心语义。

判断标准：

> 读完当前设计单元后，是否已经能正确理解它的主要输入、输出、流程、失败和边界？

如果答案是否定的，引用过度。

## 4. Definition：定义世界，不写故事

Definition 用于固定术语和语义。

推荐：

```text
Segment
草稿中对原始素材的一次引用及变换结果。
时间坐标使用片段内相对播放时间。
```

避免：

```text
在视频编辑场景中，我们首先会有素材，然后用户可能会把素材添加到草稿中，因此这里我们把……
```

定义描述“是什么”，不要记录“为什么讨论到它”。

## 5. Contract：边界优先函数化

API、CLI、能力、模块接口和模型调用优先使用接近函数签名的方式表达。

```text
find(
  targets[{id, time_range?}],
  query,
  fps?
)
  -> items[{id, time_range, ranges[{start_s, end_s, description}]}]
```

Contract 至少要让读者明确：

- 输入结构；
- 可选/必填；
- 输出结构；
- 时间、单位、ID 等关键语义；
- 非法输入和失败如何表达。

## 6. Rule / Invariant：把规范性散文降维

出现“必须、不能、始终、仅当、如果则”时，优先写明确规则。

```text
Rules:
- start_s < end_s.
- 单 target 失败不得丢失其他成功 target。
- 视觉证据不足时不得猜测台词。
```

如果多个离散条件产生不同行为，优先使用表格。

## 7. Typed Pseudocode：表达动态行为

伪代码用于表示两步以上的数据转换、调用顺序、状态变化和责任归属。

```text
effective_range<TimeRange>
  = target.time_range ?? full_range(target)

frames[Frame]
  = get_frames(target.id, effective_range, fps ?? auto)

matched_ranges[Range]
  = Model[config](query, frames)

ranges[Range]
  = validate_and_merge(matched_ranges, limit=effective_range)
```

要求：

- 左侧写真实语义，不写模糊 `result`；
- 不绑定具体编程语言；
- 不展开异常处理样板、日志调用等普通代码细节；
- 对影响语义的分支必须显式表达。

## 8. Decision Table：替代嵌套条件散文

当文本出现多个“如果……否则……”组合时，优先使用表格。

```text
| 条件 | 行为 |
| --- | --- |
| 全部成功 | success |
| 部分成功 | partial_success，保留成功和失败 item |
| 全部 target 失败 | failed，保留 item error |
| 请求级校验失败 | failed，返回顶层 error |
```

表格适合有限状态、错误矩阵、能力支持矩阵、配置组合和兼容行为。

## 9. Diagram：只表达关系，不承载唯一规范

图适合：

- 模块与依赖关系；
- 调用时序；
- 状态迁移；
- 简单数据流。

具体字段、错误码、边界值、重试语义等规则不要只藏在图中。

图应该减少理解成本，而不是为了“文档看起来专业”而存在。

## 10. Example：帮助理解，不定义规范

Example 是 illustrative，不是 normative。

如果示例出现了 Contract / Rule 中从未定义的新行为，说明规范不完整；应先补规范，再保留示例。

示例优先展示：

- 典型输入输出；
- 容易误解的边界；
- 复杂协议如何组合。

不要用大量近似示例替代规则。

## 11. Decision / Rationale：只保留有未来价值的 Why

不是所有设计都需要记录长篇理由。

只有当未来维护者可能合理地想改掉某个决定，而这个决定背后存在重要约束时，保留简短 rationale。

```text
Decision:
Events 只处理完整素材，不接受 time_range。

Reason:
Events 是可稳定缓存的完整素材粗索引；局部检索由 Find 负责。
```

讨论历史、被快速否决的方案和聊天过程通常不进入主设计文档。

## 12. Global Semantics：共享规则前置

当多个设计单元共享同一语义时，应在展开局部设计前明确一次，例如：

- ID 空间；
- 时间坐标；
- 状态含义；
- batch 基本语义；
- 安全边界；
- 内外部数据暴露原则。

局部章节仍应压缩重复与自身行为强相关的部分，避免读者必须跳转。

## 13. 压缩规则

逻辑闭合后再压缩。

优先压缩：

- 两段同义散文 -> 一条 Rule；
- 多个 if/else -> Decision Table；
- 多步流程 -> Typed Pseudocode；
- 重复模块说明 -> 一个局部 Definition + 简单关系图；
- 长篇 Why -> 两句 Decision / Reason；
- 无信息背景 -> 删除。

不要压缩掉：

- 失败行为；
- 边界；
- 责任归属；
- 状态语义；
- 一致性；
- 兼容性；
- 资源上限；
- 重要未知项。

## 14. 一个事实是否适合引用

优先直接压缩表达；只有满足以下情况之一时才考虑引用：

- 完整枚举很长，而局部只需要其中一个结论；
- 内容属于背景证据而非当前行为；
- 同一份机器可读 schema / 协议必须保持唯一来源；
- 低频实现细节不值得复制进主阅读路径。

即使引用，当前段落也必须先给出足够完成局部理解的压缩结论。
