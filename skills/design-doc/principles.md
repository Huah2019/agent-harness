# Design Writing Principles

本文件补充 `design-doc` 的写作原则。目标是让开发设计文档同时满足两件事：**人容易 Review，Codex 容易准确实现**。

文档应优先降低歧义、跳转和无效上下文，而不是追求形式上的完整或专业感。

## 1. 先保证语义完整，再考虑文档形式

设计文档必须覆盖当前需求实现所需的重要语义，但不要求固定章节、固定长度或固定模板。

评价一份设计时，优先判断：

- Reviewer 能否快速理解背景、目标和关键方案；
- Codex 是否仍需自行决定会影响行为正确性的设计；
- 是否存在只有作者知道的隐藏前提；
- 是否只描述了正常路径；
- 是否存在多种合理解释而文档没有明确；
- 是否需要依赖此前聊天才能理解。

## 2. 设计文档是最终设计的压缩表达

文档不是需求讨论和推理过程的记录。

保留最终成立的背景、定义、规则、数据流、边界、失败语义、状态和关键取舍；删除为了记录“怎么一路讨论到这里”而产生的过程信息。

复杂设计可以很长，但每一段都应该帮助 Review 或改变实现方式。

## 3. 信息局部性优先

局部设计应尽量自洽。

重复一个压缩后的关键规则，通常比要求读者跨多个章节跳转更容易理解。引用适合完整枚举、低频细节和补充背景，不应承担局部核心语义。

判断标准：

> 读完当前设计单元后，是否已经能正确理解它的主要职责、输入、输出、流程、失败和边界？

如果答案是否定的，说明局部信息不足或引用过度。

## 4. Definition：定义世界，不写故事

Definition 用于固定术语和语义。

推荐：

```text
Segment
草稿中对原始素材的一次引用及变换结果。
时间坐标使用片段内相对播放时间。
```

避免：

```text
在视频编辑场景中，我们首先会有素材，然后用户可能会把素材添加到草稿中，因此这里我们把……
```

定义描述“是什么”，不要记录讨论过程。

## 5. Contract：边界优先函数化

API、CLI、能力、模块接口和模型调用优先使用接近函数签名的方式表达。

```text
find(
  targets[{id, time_range?}],
  query,
  fps?
)
  -> items[{id, time_range, ranges[{start_s, end_s, description}]}]
```

Contract 至少让 Reviewer 和实现者明确：

- 输入结构；
- 可选和必填字段；
- 输出结构；
- 时间、单位、ID 等关键语义；
- 非法输入和失败如何表达。

## 6. Rule / Invariant：把规范性散文降维

出现“必须、不能、始终、仅当、如果则”时，优先写明确规则。

```text
Rules:
- start_s < end_s.
- 单 target 失败不得丢失其他成功 target。
- 视觉证据不足时不得猜测台词。
```

如果多个离散条件产生不同行为，优先使用表格。

## 7. Typed Pseudocode：表达动态行为

伪代码用于表示两步以上的数据转换、调用顺序、状态变化和责任归属。

```text
effective_range<TimeRange>
  = target.time_range ?? full_range(target)

frames[Frame]
  = get_frames(target.id, effective_range, fps ?? auto)

matched_ranges[Range]
  = Model[config](query, frames)

ranges[Range]
  = validate_and_merge(matched_ranges, limit=effective_range)
```

要求：

- 左侧写真实语义，不写模糊 `result`；
- 不绑定具体编程语言；
- 不展开日志、样板错误处理等普通代码细节；
- 影响行为的分支必须显式表达；
- 伪代码本身应容易人工 Review。

## 8. Decision Table：替代嵌套条件散文

当文本出现多个“如果……否则……”组合时，优先使用表格。

```text
| 条件 | 行为 |
| --- | --- |
| 全部成功 | success |
| 部分成功 | partial_success，保留成功和失败 item |
| 全部 target 失败 | failed，保留 item error |
| 请求级校验失败 | failed，返回顶层 error |
```

表格适合有限状态、错误矩阵、能力支持矩阵、配置组合和兼容行为。

## 9. Diagram：只在能降低理解成本时使用

图适合：

- 模块与依赖关系；
- 调用时序；
- 状态迁移；
- 简单数据流。

具体字段、错误码、边界值、重试语义等规则不要只藏在图中。

图的价值是让 Reviewer 更快建立整体关系，而不是让文档看起来更正式。

## 10. Example：帮助理解，不代替规则

Example 用于帮助理解典型行为。

如果示例出现了 Contract / Rule 中从未定义的新行为，说明设计仍不完整；应先补规则，再保留示例。

示例优先展示：

- 典型输入输出；
- 容易误解的边界；
- 复杂协议如何组合。

不要用大量近似示例替代规则。

## 11. Decision / Reason：只保留有价值的 Why

不是所有决定都需要记录长篇理由。

当 Reviewer 或未来维护者很可能问“为什么不是另一种方案”，且这个选择背后存在重要约束时，保留简短理由。

```text
Decision:
Events 只处理完整素材，不接受 time_range。

Reason:
Events 是稳定的完整素材粗索引；局部检索由 Find 负责。
```

讨论历史和已经失去价值的候选方案通常不进入主设计文档。

## 12. 共享语义优先说明

当多个设计单元共享同一语义时，应在展开局部设计前明确，例如：

- ID 空间；
- 时间坐标；
- 状态含义；
- batch 基本语义；
- 安全边界；
- 内外部数据暴露原则。

局部章节仍可压缩重复与自身行为强相关的部分，保证局部可读。

## 13. 压缩规则

逻辑闭合后再压缩。

优先压缩：

- 两段同义散文 -> 一条 Rule；
- 多个 if/else -> Decision Table；
- 多步流程 -> Typed Pseudocode；
- 重复模块说明 -> 一个 Definition + 简单关系图；
- 长篇 Why -> 两句 Decision / Reason；
- 无信息背景 -> 删除。

不要压缩掉：

- 必要背景；
- 失败行为；
- 边界；
- 责任归属；
- 状态语义；
- 一致性；
- 兼容性；
- 资源上限；
- 重要未知项。

## 14. 引用规则

优先直接给出当前阅读位置所需的压缩结论。只有以下情况适合进一步引用：

- 完整枚举很长，而局部只需要其中一个结论；
- 内容属于补充背景而非当前行为；
- 同一份机器可读 schema / 协议需要保持唯一来源；
- 低频细节不值得复制进主阅读路径。

即使引用，当前段落也必须先包含足够完成局部理解的关键信息。
